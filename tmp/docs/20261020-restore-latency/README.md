# gVisor / Cellbox / CoCell 恢复延迟优化报告

测量日期：2026-10-16、2026-10-20。报告整理日期：2026-10-20。所有耗时单位均为毫秒（ms）。

## 结论

- **已有 Cellbox 预创建池时，两个核心改动合计减少约 479 ms（68.9%）。** 使用 no-root、延迟绑定 checkpoint，并关闭内部后台页扫描后，512 MiB 测试程序的首响应均值从 **694.98 ms 降至 216.16 ms**。
- **把预创建池对恢复请求路径的收益纳入比较，首响应合计减少约 967 ms（81.7%）。** 无池 root/eager 的首响应均值是 **1183.05 ms**。216.16 ms 是池命中后的恢复延迟；建池、调度和拉镜像等首次创建成本并未全部计入。
- **保留“预创建池 + no-root + lazy”作为默认组合，整文件并行预读默认关闭。** 本轮并行预读让首响应增加 **39.57 ms**，但让完整 512 MiB 状态校验提前 **168.79 ms**，适合由调用方按访问模式选择。
- **真实 CoCell 的历史测试也支持仅按需加载，但不能直接套用 81.7%。** 首次向模型服务发出请求的中位耗时从 **666.85 ms 降至 500.74 ms**；加 checkpoint 专属 hotset 并行预读后为 **466.84 ms**。这组数据没有包含新的 no-root 对照，也不是模型首 token 延迟。

**证据限制：** 2026-10-20 的 70 行原始样本目录本次未找回，但完整执行汇总和配对统计仍在，已保存为本目录的 JSON 附件。本报告重新核算了汇总间的差值，没有声称重新计算这 70 行的均值或置信区间。2026-10-16 的 40 行真实 CoCell 原始计时字段已全部保留并重新计算。

## 1. 两个核心改动与 Cellbox 预创建分别做什么

| 措施 | 行为与目的 |
| --- | --- |
| Cellbox 预创建运行时池 | 在恢复请求前准备好可复用的运行时，把部分初始化移出请求的等待路径；池的准备仍有成本。 |
| no-root、延迟绑定 checkpoint | 先准备不含业务 root checkpoint 的 Sentry，在真正恢复业务容器时再传入对应 checkpoint，便于复用预创建实例。 |
| lazy 按需页加载 | 关闭 gVisor 内部的推测性后台页扫描；真正访问的页面仍然按需加载。 |
| 外部页面预读，可选 | Cellbox 或独立进程把 checkpoint 内容读入宿主机 page cache；这不等于页面已装入 Sentry 的 MemoryFile。 |

“预创建运行时池”和“预读 checkpoint 页面”是两项不同的能力。当前推荐组合启用前者，整文件预读默认关闭。页加载器唤醒修复包含于最终对照的同一个 runtime 中，没有单独移除它的性能对照，因此不能给它单列一个节省数值。

## 2. 三种计时终点

2026-10-20 的七组测试均从 **resume POST 开始**计时：

| 指标 | 结束条件 | 含义 |
| --- | --- | --- |
| restore 操作完成 | API operation 完成 | 不代表应用已经响应，也不代表全部内存已经读完。 |
| 首次应用响应 | 首个成功的 health HTTP 响应完成 | 本报告主要讨论的响应延迟。 |
| 完整状态校验 | health 成功后，读取并校验全部 512 MiB 应用状态完成 | 包含前两个阶段，展示后续访问完整内存的代价。 |

三个指标是累计终点，不能相加。池的创建与就绪、策略切换都在触发计时前。提前全量预热组的预热也在触发前，其成本在第 6 节单列。

## 3. 分项收益：按固定顺序观察到的增量

七组各 10 次，按随机化轮次执行，共 70 次性能恢复。以下正数表示节省，负数表示变慢。

| 措施，按表列顺序叠加 | 首响应均值节省 | 操作完成均值节省 | 完整校验均值节省 | 首响应同轮更快 |
| --- | ---: | ---: | ---: | ---: |
| 加入预创建池 | 488.07 | 487.51 | 481.76 | 10/10 |
| 再关闭内部后台页扫描（lazy） | 166.11 | 443.55 | -23.83 | 5/10 |
| 再使用 no-root / 延迟绑定 checkpoint | 312.70 | 37.71 | -1.74 | 9/10 |
| 可选：再加并行整文件预读 | -39.57 | -42.48 | 168.79 | 1/10 |

前三步按未四舍五入的数据计算，首响应合计减少 **966.89 ms**。若起点已经有预创建池，只计算后面两个核心改动，则是 **478.81 ms**。

**这些是这条配置路径上的观测增量，不是可以换序相加的独立因果贡献。** root/no-root 分别创建 Box，使用同模板、镜像与负载逻辑，但各自保存并滚动使用自己的 checkpoint。同一轮的配对是匹配回合，不是同一个 checkpoint 的字节级对照；它也不能排除两个 Box 的全部差异。

## 4. 七组完整结果

每组 n=10；前面三列为均值，另列首响应中位数和范围。原始汇总见 [recorded-final-aggregates.json](recorded-final-aggregates.json)，机器可读表见 [latency-summary.csv](latency-summary.csv)。

| 配置 | 操作完成均值 | 首响应均值 | 完整校验均值 | 首响应中位数 | 首响应范围 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 无预创建池 / root / eager | 1166.61 | 1183.05 | 1456.15 | 1163.60 | 1116.50–1366.22 |
| 预创建池 / root / eager | 679.10 | 694.98 | 974.39 | 686.57 | 641.16–751.95 |
| 预创建池 / root / lazy | 235.55 | 528.86 | 998.22 | 708.40 | 189.44–781.85 |
| 预创建池 / no-root / eager | 674.19 | 732.67 | 1015.30 | 736.57 | 623.29–833.83 |
| 预创建池 / no-root / lazy（默认组合） | 197.83 | 216.16 | 999.96 | 217.46 | 198.07–229.29 |
| 默认组合 + 并行整文件预读 | 240.32 | 255.74 | 831.17 | 254.88 | 221.56–279.78 |
| 默认组合 + 提前全量预热 | 189.60 | 203.31 | 536.17 | 204.96 | 190.69–213.38 |

推荐默认组合的首响应为 **216.16 ms**，但完整状态校验仍约 **999.96 ms**。相对已有池 root/eager 的完整校验 974.39 ms，它并没有提前完成全部内存访问，而是让应用可以先响应，再为后续真正访问的页面付读取成本。

## 5. no-root 与 lazy 的交互

已有预创建池时，首响应均值如下：

| 页面策略 | root | no-root | 使用 no-root 的节省 |
| --- | ---: | ---: | ---: |
| eager，保留内部后台扫描 | 694.98 | 732.67 | -37.69 |
| lazy，仅按需读取 | 528.86 | 216.16 | 312.70 |

不能把 no-root 的收益固定写成“每次节省 313 ms”：在 eager 下，它的首响应均值反而增加了 37.69 ms；在 lazy 下才观察到较大改善。

root/lazy 的首响应均值为 528.86 ms，但中位数是 708.40 ms，高于 root/eager 的 686.57 ms；范围为 189.44–781.85 ms，仅 5/10 个匹配回合更快。no-root/lazy 的 10 次首响应范围为 **198.07–229.29 ms**。这支持采用组合方案，但 n=10 不足以给出生产 p99 或故障率承诺。

在操作完成口径中，lazy 的顺序增量是 **443.55 ms**，随后 no-root 是 **37.71 ms**。首响应口径中的 312.70 ms 不能全部解释为缩短了 runtime 初始化。

## 6. 外部预读与提前预热的成本

### 并行整文件预读

相对默认 no-root/lazy：

- 首响应：216.16 → 255.74 ms，增加 **39.57 ms**，只有 1/10 个匹配回合更快。
- 完整状态校验：999.96 → 831.17 ms，节省 **168.79 ms**，10/10 个匹配回合都更快。

这是与恢复重叠的预读尝试，不能当成触发前已经把全部文件读完。它对首响应与完整内存读取的影响不同，因此继续默认关闭，让调用方按后续访问模式选择。

### 提前全量预热

| 指标 | 均值 |
| --- | ---: |
| 触发前预热成本 | 421.59 |
| 触发后首响应 | 203.31 |
| 预热成本 + 首响应 | 624.90 |
| 触发后完整状态校验 | 536.17 |
| 预热成本 + 完整状态校验 | 957.75 |

只有可以提前或重叠支付预热成本时，才适合引用触发后的 203.31 ms；不能把它当成无成本的整体恢复时间。预创建池同样提前支付准备成本，本次没有可确认的通用建池耗时汇总。

## 7. 真实 CoCell / Codex app-server 的补充证据

这部分来自 **2026-10-16 的 40 次评估 + 3 次独立 hotset 训练恢复**。四组各 10 次，采用同一个不可变 checkpoint、同一镜像与应用调用流程，每轮顺序随机。

计时从恢复 trigger 开始，到 loopback 转发代理收到首个真实 `POST /v1/responses` 为止。包含 CRI 恢复和 `initialize → thread/resume → turn/start`，排除 Pod 调度、镜像拉取、客户端启动、完整 CoCell 控制平面和下游模型推理。因此它衡量首次向 provider 发出请求的时间，**不等于模型首 token 或完整模型响应时间**。

| 配置 | 请求发出中位数 | 均值 | 范围 |
| --- | ---: | ---: | ---: |
| 原版内部后台加载 | 666.85 | 671.50 | 648.01–714.08 |
| 仅按需加载 | 500.74 | 503.89 | 487.22–532.36 |
| 按需加载 + 整文件预读 | 551.30 | 557.03 | 523.91–636.94 |
| 按需加载 + hotset 预读 | 466.84 | 466.92 | 438.76–503.68 |

按未四舍五入的组中位数计算：

- 仅按需加载比原版减少 **166.12 ms（24.9%）**。
- hotset 在仅按需加载之上再减少 **33.90 ms**，相对原版共减少 **200.02 ms（30.0%）**。
- 整文件预读比仅按需加载增加 **50.57 ms**。

“两个组的中位数之差”和“逐轮配对差值的中位数”是不同统计量，下面分别列出：

| 配置变化 | 组中位数之差，节省 | 配对节省中位数 | 同轮更快 |
| --- | ---: | ---: | ---: |
| 原版内部后台加载 → 仅按需加载 | 166.12 | 160.85 | 10/10 |
| 仅按需加载 → 按需加载 + 整文件预读 | -50.57 | -36.08 | 0/10 |
| 仅按需加载 → 按需加载 + hotset 预读 | 33.90 | 34.99 | 10/10 |
| 原版内部后台加载 → 按需加载 + hotset 预读 | 200.02 | 199.78 | 10/10 |

hotset 在全部 10 个同 checkpoint 配对回合中都优于仅按需加载；整文件预读在全部 10 回合中都更慢。hotset 为三次独立训练到首次请求发出时，checkpoint 页缓存驻留范围的并集，约 **56.9 MiB**，包含 runtime 访问和 readahead；它不是精确的单个应用进程工作集，只适用于这个 checkpoint，也不代表当前默认实现会自动学得生产 hotset。

预读与恢复 trigger 同时开始，使用一个 worker，512 MiB/s 是逻辑触页速率，不是硬设备带宽限制。hotset 预读中位约 115 ms 完成；三次训练也有成本，本次没有把它们汇总成一个可引用的训练时长。

## 8. 测试条件、版本与正确性范围

### 2026-10-20 七组对照

- k3s/systrap；512 MiB 应用状态；sandbox CPU 上限 2 核、内存上限 2 GiB。
- 当时脚本清理 checkpoint 文件的 Linux 页缓存，并以 `mincore` 验证为冷；VM 底层存储缓存未控制。
- root/no-root 分别创建 Box，并各自保存、滚动和消费自己的 checkpoint。
- 两次额外的池未命中检查仅用于 fallback 功能验证，不纳入七组性能统计。
- 当时执行记录报告 70 次性能恢复及状态校验成功，并检查预创建 Sentry 的 PID 复用、checkpoint GC 后按需读和清理。由于原始样本目录缺失，本次没有重新逐样本验证这些正确性记录。
- runtime 源版本：[`4320a3de3afb`](https://github.com/jingyugao/gvisor/commit/4320a3de3afb26889f0a0d28787107e9f299c0f4)。Cellbox 版本：`c428c94eb1660284a5359f7d4730c0d0220cdb78`。唤醒修复包含于所有七组，没有独立性能消融。

### 2026-10-16 真实 CoCell

- 应用与 rootfs 缓存保持热；checkpoint 页缓存由 `mincore` 验证为冷；VM 底层存储缓存未控制。
- 另有 500 MiB 已写入匿名内存的空闲进程；`pages.img` 为 561.36 MiB；没有 Pod CPU/memory requests 或 limits。
- 原始检查记录显示 40 次真实 provider 请求和完成通知、应用进程身份、500 MiB 内存校验均通过。现存两个分析文件共 525 条不重名的通过记录、0 条问题；旧文字中的 441 条计数无法由现存证据重现，本报告采用原始文件计数。
- 原版源码：`0e89e080d86336659595020d36ab938fe69acb00`；按需加载实验源码：`f00784c266cde99ba816293776449c000945cd90`。
- 为复用原版同一个 checkpoint，补丁二进制刻意使用原版 version stamp；真实 commit 与二进制 SHA 另行保存。这不是跨任意版本 checkpoint 兼容性的证明。

## 9. 尚未量化的范围

**尚未有同版本真实 CoCell 的 no-root / lazy / 预创建池全套分项对照，也没有量化模型首 token。** 不能把 512 MiB 测试程序的 81.7% 直接当作真实 CoCell 完整会话的加速比例。

补足这部分结论需要在同版本真实 CoCell 上，以相同业务状态比较这些配置，并同时记录恢复、首次 provider 请求和首 token。本报告没有运行新实验，也没有把唤醒修复、CI 或部署适配折算成性能收益。
